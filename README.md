# Granite Decisions

**v0.1.0 — a trainable local typed-decision research starter built on IBM Granite 4.1 3B.**

Run Choice, Score, and Noul decisions locally; train task-specific heads; or experiment
with optional ROCm LoRA fine-tuning. This release contains the implementation and
training recipes, not a new pretrained checkpoint. It does not yet match Jev.
See [MODEL_CARD.md](MODEL_CARD.md) for intended use and measured limitations.

For Fedora Atomic with an AMD GPU, clone the repository, run
`bash deploy/setup-toolbox.sh`, and follow [TRAINING.md](TRAINING.md).
For tests only: `python3 -m venv .venv`, install with
`.venv/bin/pip install -e ".[serve,test]"`, then run
`.venv/bin/python -m unittest discover -s tests -v`.

The original synthetic datasets are published with this source under
[validation/hyde-20260917/synthetic-data](validation/hyde-20260917/synthetic-data/README.txt),
with the reproducible [generator](scripts/make_smoke_data.py). They are smoke tests,
not independent evidence of production quality.

An independent, MIT-licensed implementation of typed decision inference on
**IBM Granite 4.1**, using **native ROCm llama.cpp on Fedora** as the deployment
target. `granite-decisions` is a descriptive working name, not a cleared brand.

This package includes runnable inference, head training, calibration, evaluation,
HTTP and JSONL interfaces, a feedback journal, and a Fullcollar 0.1.0 adapter.
It does not include a newly trained general-purpose model or IBM's model weights.
The real Granite 4.1 3B Q4_K_M model was exercised on CPU during development.
Hyde ROCm execution, head training, a live Jev comparison, and optional PyTorch
LoRA training are now exercised. See [TRAINING.md](TRAINING.md) for the tested
Fedora Atomic Toolbx setup, results, and limits; `VALIDATION.md` retains the
earlier CPU evidence. The synthetic tests do not establish production quality.

## What is implemented

| Capability | Implementation |
| --- | --- |
| Choice | Probability distribution over a supplied finite set, plus argmax label |
| Score | Distribution over ordered rubric levels; score is the expected zero-based level |
| Noul | Probability of a binary proposition being true |
| Initial classifier | One constrained output token per question; arbitrary questions, up to 26 options |
| Trained fast path | One Granite hidden-state vector per input; independent learned categorical heads return the requested registered fields |
| Calibration | Per-head temperature scaling on a separate labeled split |
| Evaluation | Accuracy, NLL, Brier score, ECE, selective error, coverage, Wilson interval, latency |
| Feedback | Append-only SQLite success/failure/unknown events; explicit verified labels for training export |
| Interfaces | Python, JSONL process, HTTP, Fullcollar provider |

The trained path uses a frozen Granite backbone and regularized softmax linear
heads. NumPy/SciPy train the small heads on CPU; **llama.cpp performs all backbone
inference**, including feature extraction on ROCm. The inference/head-training library has no PyTorch, vLLM, Ollama, or hosted
inference dependency. The tested Fedora Atomic setup uses Toolbx for ROCm build
tools. Optional backbone fine-tuning uses a separate ROCm PyTorch environment,
and the optional Jev benchmark makes explicitly requested hosted API calls.

These are classification features from a causal language model, not claims of a
purpose-trained retrieval embedding model. Their usefulness must be measured on
your labeled tasks. New question content requires new heads; callers can rename,
reorder, repeat, or select a subset of trained questions without retraining. The baseline
supports new schemas immediately, with weaker efficiency and no fitted calibration.

## Scope relative to Jev

Jev's public interface motivates the Choice/Score/Noul shapes. This is our own
implementation and HTTP/CLI interface, not an exact TypeSafe SDK replacement.
Jev's proprietary weights, architecture, sampler, training data, and RLCD method
are not reproduced. Its performance claims do not transfer to this project.
The main remaining gap is general-purpose, question-conditioned inference with
isolated parallel evaluation. See `TYPESAFE-COMPATIBILITY.md` for the checked
contract, remaining architecture work, and limits of this initial implementation.

The trained heads avoid output-token decoding: one state encoding feeds all
heads. The baseline still samples one token per question, ignores the sampled
value, and derives its answer from the complete candidate distribution. Questions
are evaluated sequentially in this baseline. No output explanations or JSON
strings are generated by the model; Python constructs the typed response.

Typed output prevents out-of-schema labels. It does **not** prevent an incorrect
in-schema judgment. `confidence` here means one minus normalized entropy; it is
not an empirical correctness probability and does not claim Jev's formula.
The top-level `calibration` field distinguishes unfitted token probabilities from
temperature-fitted heads. Temperature fitting does not prove deployment calibration.

## Run on Hyde

The verified Hyde project directory is `~/Development/granite-decisions`.
On Fedora Atomic, start with `bash deploy/setup-toolbox.sh` and follow
[TRAINING.md](TRAINING.md). On a host with the native prerequisites already
installed, run:

```bash
bash deploy/run-hyde.sh
```

The runner checks the host, builds pinned native ROCm llama.cpp, installs the
Python package in a local virtual environment, runs tests, downloads or verifies
IBM's pinned 3B GGUF, and runs the real-model interface smoke test. It saves all
step logs, native server logs, a JSON result, and an exit code under a new
`runs/hyde.*` directory. Stop at the first failed step and inspect its log.
This does not install missing Fedora packages; rerun after addressing the
reported prerequisite. Overrides: `GD_NATIVE_ROOT`, `GD_VENV`, `GD_MODEL_DIR`,
`GD_GPU_TARGET`, and `GD_JOBS`.

For the individual steps, follow the commands below. Existing ROCm, Fedora
package versions, paths, and device access must be
checked on Hyde; they were not inferred from its older Arch configuration.
The scripts preserve existing installations and build in a separate `.native`
directory. They do not install system packages or change drivers, firmware,
memory reservations, network settings, or existing services.

Prerequisites: Python 3.11+, git, CMake, a C/C++ compiler, ROCm development libraries
including HIP/hipBLAS/rocBLAS, `hipconfig`, `rocminfo`, and access to `/dev/kfd` and
the render device. Use the preflight to identify actual missing components.

```bash
cd ~/src/granite-decisions
bash deploy/hyde-native.sh inspect
bash deploy/hyde-native.sh build
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[serve,test]'
python3 scripts/download_granite.py --directory models
```

The build discovers the GPU target from `rocminfo`, rather than forcing a target
or an HSA compatibility override. If more than one target is present, explicitly
set `GD_GPU_TARGET` to the intended one. The expected `gfx1151` for Strix Halo is
an expectation, not an observation of Hyde in this session. `GD_JOBS` defaults to 8.

The model download is IBM's official 3B Q4_K_M GGUF at an immutable repository
revision. It is roughly 2.1 GB. Preserve the upstream Apache-2.0 license when
redistributing weights. Other Granite 4.1 sizes can use the same interfaces after
conversion/download and a fresh bind, training run, and evaluation.

First validate the native installation:

```bash
.venv/bin/python scripts/smoke_native.py \
  --server "$PWD/.native/build-rocm/bin/llama-server" \
  --gguf "$PWD/models/granite-4.1-3b-Q4_K_M.gguf" \
  --out hyde-smoke.json
```

This launches temporary localhost servers on ports 19091 and 19092, verifies a
reported ROCm device, tests all three primitives, extracts real Granite features,
fits a tiny test head, saves a report, and stops both servers. It requires both
a listed ROCm device and positive layer-offload evidence in each server's load
log. Logs are retained under `OUT.logs` or `--log-dir`; missing offload evidence
fails the run. This log check is not a driver-performance benchmark. Do not use its four illustrative
training examples as a decision-quality evaluation.

## Use the initial classifier

In one terminal, run the native baseline server in the foreground:

```bash
bash deploy/serve-native.sh \
  "$PWD/.native/build-rocm/bin/llama-server" \
  "$PWD/models/granite-4.1-3b-Q4_K_M.gguf" baseline
```

In another terminal, after the server reports it is ready:

```bash
.venv/bin/granite-decisions bind --url http://127.0.0.1:8092 \
  --gguf "$PWD/models/granite-4.1-3b-Q4_K_M.gguf" \
  --mode baseline --out baseline-runtime.json
.venv/bin/python - <<'PY'
import json
from pathlib import Path
request = {
    "state": {"request": "Write a Python function that adds two integers."},
    "questions": json.loads(Path("examples/questions.json").read_text()),
}
Path("request.json").write_text(json.dumps(request))
PY
.venv/bin/granite-decisions infer --url http://127.0.0.1:8092 \
  --runtime baseline-runtime.json --request request.json
```

The response contains actual model probabilities and `status: abstained` until
you explicitly permit uncalibrated experimentation. `--allow-uncalibrated` permits
advisory proposals above the configured probability and margin thresholds; it
never grants execution authority. The default probability threshold is 0.85 and
margin is 0.10. These are starting settings, not validated deployment thresholds.

`--jsonl` reads one request per stdin line and writes one response per line while
keeping the backend configuration loaded. Recoverable per-request errors produce
an `error` object. Context overflow raises an error instead of truncating input.

## Train the shared decision heads

Stop the baseline server if conserving memory. Start the embedding server:

```bash
bash deploy/serve-native.sh \
  "$PWD/.native/build-rocm/bin/llama-server" \
  "$PWD/models/granite-4.1-3b-Q4_K_M.gguf" embedding
```

Bind that server separately, on its default port 8091:

```bash
.venv/bin/granite-decisions bind --url http://127.0.0.1:8091 \
  --gguf "$PWD/models/granite-4.1-3b-Q4_K_M.gguf" \
  --mode embedding --out embedding-runtime.json
```

Prepare three JSONL datasets following `examples/training-format.jsonl`. Each row
has `id`, `state`, and one independently verified label per question. Choice labels
are strings, Noul labels are booleans, and Score labels are integer level indexes.
The four provided rows illustrate the format; they are not a sufficient dataset.

Use independently sampled train, calibration, and test sets. Keep related tickets,
customers, conversations, documents, and near-duplicate paraphrases in one split.
The loader detects repeated IDs and exact canonical state duplicates across
splits. It cannot detect semantic duplicates or shared provenance automatically.
Do not insert random IDs into the state to defeat the duplicate check.

The implementation requires at least 20 training, 50 calibration, and 50 test
examples, with every class represented in every split. These are mechanical
minimums, not statistical sample-size recommendations. Rare or consequential
errors may require substantially larger independent evaluation sets.

```bash
.venv/bin/granite-decisions train --runtime embedding-runtime.json \
  --questions examples/questions.json \
  --train data/train.jsonl --calibration data/calibration.jsonl \
  --test data/test.jsonl --out artifacts/candidate-001
```

Training saves `heads.npz`, `manifest.json`, and `evaluation.json`. It does not
activate the candidate or update a running process. The manifest binds the schema,
GGUF digest, llama.cpp build, pooling, requested GPU-layer configuration, prompt
version, dataset hashes, temperatures, and head weights. Artifacts do not contain
raw input states. Do not reuse them after changing the quantization, driver/runtime
behavior, feature rendering, or question content; retrain/recalibrate and reevaluate.
Train each distinct question definition once. Inference can reuse that head
under different question IDs, including more than one alias in a request.

Select a reviewed bundle explicitly:

```bash
.venv/bin/granite-decisions infer --runtime embedding-runtime.json \
  --bundle artifacts/candidate-001 --request request.json
.venv/bin/granite-decisions serve --runtime embedding-runtime.json \
  --bundle artifacts/candidate-001 --journal decisions.sqlite
```

The API binds to `127.0.0.1:8093`. POST
`{"model": "ibm-granite/granite-4.1-3b", "state": ..., "questions": ...}` to
`/v1/decisions` or `/v1/systemone`. It accepts one active model request, returns
503 when busy, 400 for invalid JSON or oversized bodies, and 422 for contract
violations. `model` is optional and must match the loaded model when supplied;
it cannot load a different model, and `jev-latest` is not an alias for Granite.
`examples/systemone-request.json` shows a mixed structured request.
Policies and model paths
are configured by the operator, never by request payloads. Set
`GRANITE_DECISIONS_API_KEY` for API authentication and `LLAMA_API_KEY` for the
native server. Use an SSH tunnel for remote callers; the Python native client
accepts loopback endpoints only.

All outputs are advisory. Fullcollar or the calling application owns action
authorization, hard constraints, escalation, and execution. A probability is not
an authorization token. Do not multiply field probabilities to claim joint
confidence; the heads share a representation and may have correlated errors.

## Evaluate and learn from feedback

```bash
.venv/bin/granite-decisions evaluate --runtime embedding-runtime.json \
  --bundle artifacts/candidate-001 --questions examples/questions.json \
  --data data/new-test.jsonl --out evaluation-new.json
```

The report flags overlap with the bundle's train/calibration/test states and
reports whole-request coverage separately from per-field threshold coverage.
Per-field coverage does not include the `unknown` choice or global calibration
gate. Accuracy and probabilities should be compared against a majority-class
baseline, a cheap open classifier, and actual Fullcollar workflow outcomes before
spending more inference compute. Benchmark cold/warm latency and input lengths
on Hyde; the included smoke timings are not representative workload benchmarks.

To retain replayable inputs, start inference/serving with both `--journal` and
`--record-state`. Without explicit state retention, the journal stores state hashes,
questions, outputs, and feedback but cannot export raw-state training examples.

Feedback JSON contains `decision_id`, `verdict` (`success`, `failure`, or `unknown`),
`labels`, `reviewer`, and `note`. `success`/`failure` refer to the reviewer's observed
outcome; labels are explicit verified classification targets. They are not
automatically inferred from a reward, a positive comment, or the model's own output.

```bash
.venv/bin/granite-decisions feedback --journal decisions.sqlite --event feedback.json
.venv/bin/granite-decisions export-feedback --journal decisions.sqlite --out reviewed.jsonl
```

Every feedback event remains in the journal. The most recent explicit review
determines an example's current export label; an `unknown` review withdraws it
from training export. Split exported examples by provenance and time before a
new train/calibrate/test cycle. Preserve a frozen test set outside this loop.
SQLite append-only triggers prevent accidental update/delete through ordinary
SQL; the journal is not a tamper-proof cryptographic ledger.

## Fullcollar

`granite_decisions.fullcollar.GraniteProvider` implements the inspected
Fullcollar 0.1.0 `evaluate(state, questions)` contract. Install Fullcollar separately.
`examples/fullcollar_shadow.py` demonstrates the initial baseline in shadow mode.
The default provider blocks an abstained response by raising Fullcollar's
`ProviderError`; Fullcollar 0.1.0 records that as an error with no decision because
its provider interface does not propagate an abstention status directly.
The `shadow_engine` factory permits inspection of raw answers and fixes the
Fullcollar engine to shadow mode. No existing Fullcollar files were modified.

## Why the llama.cpp patch is required

The pinned upstream revision uses grammar rejection sampling: when a sampled
token already satisfies the grammar, it need not mask other token probabilities.
The real-model test observed an invalid `0` token in top probabilities for an
`A | B | C` grammar. Treating those scores as a complete choice distribution would
be incorrect. `patches/llama-grammar-probabilities.patch` requests grammar-first
sampling when post-sampling probabilities are requested, and exposes capability,
pooling, and requested GPU-layer metadata. Only the ordinary sampling path is
patched; these launchers do not enable speculative decoding or backend sampling.

The client requires the patch marker for baseline inference, verifies the pooling
mode for learned heads, and rejects missing candidate probabilities. It does not
fill missing choices with invented zeros or silently normalize a partial top-k.
The feature server does not need the sampling change, but uses the same patched
build to expose its actual pooling configuration. A server fingerprint is not
remote attestation: operators must bind the actual loaded model file, avoid
replacing weights behind the same path, and rebind after intentional changes.
